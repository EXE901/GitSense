6. OAUTH ADJUSTMENTS
================================================================

OAuth architecture is unchanged. Only the URLs change.

Required GitHub OAuth app (one per environment, GitHub does
not allow multiple callback URLs):

  Production OAuth app:
    Homepage URL              https://gitsense.tech
    Authorization callback    https://api.gitsense.tech/auth/oauth/github/callback

  Local-dev OAuth app:
    Homepage URL              http://localhost:3000
    Authorization callback    http://localhost:8000/auth/oauth/github/callback

The backend then redirects the browser to
FRONTEND_GITHUB_CALLBACK_URL after the handshake completes.

Google OAuth (optional) follows the same pattern. Authorized
JavaScript origins must include the frontend origin; authorized
redirect URIs must include the backend callback URL.


================================================================
7. COOKIES & CROSS-ORIGIN AUTH
================================================================

GitSense's authenticated flow does NOT rely on cross-origin
cookies, so the production split between gitsense.tech and
api.gitsense.tech works without browser cookie gymnastics:

  - Access token: stored in localStorage, sent as
    `Authorization: Bearer <jwt>` header.
  - Guest session: stored in localStorage, sent as
    `X-Guest-Session-Id` header.
  - The backend's `gitsense_guest_session_id` cookie
    (secure=False, samesite="lax") is a same-origin
    convenience only. In production it will not round-trip
    between gitsense.tech and api.gitsense.tech — and it does
    not need to, because the header path covers all flows.

  No change made to the cookie configuration. Setting
  samesite="none" + secure=True would require HTTPS in dev
  and would not provide any new capability the headers do not
  already provide.

12. RISKS / BLOCKERS
================================================================

  - Database migrations: backend currently relies on init_db()
    at startup. For production schema changes, introduce
    Alembic. Out of scope for this pass.
  - Per-worker briefing cache: each uvicorn worker keeps its
    own 90s cache. Acceptable for single-instance Railway
    deployments; needs Redis for multi-instance scaling.
  - CORS_ALLOW_ORIGINS uses an exact-match list. If Vercel
    preview deployments need to hit the production API, add
    each preview origin or a regex-aware origin policy. Not
    required for the initial production cut.
  - OpenRouter free tier may rate-limit under sustained
    traffic. Behavior is already bounded (10 s outer timeout
    + deterministic fallback). No deployment risk.
  - Backend secrets currently in backend/.env (local) must NOT
    be reused in production — generate fresh values for
    JWT_SECRET_KEY and the OAuth client secrets before going
    live. The .env file is gitignored so this is not a leak,
    but operators should rotate.
